# PA — распределённый тулинг: вижен (мозг на Synology + удалённые ноды)

**Тип документа:** внутренний архитектурный вижен — не утверждённый эпик, не обязательство к реализации.  
**Статус:** черновик для обсуждения  
**Дата:** 2026-04-07  
**Связанные материалы:** `ai-sdlc/` (пайплайн, skills, `tools/validate`), текущая модель тулов PA (`internal/toolcatalog`, `internal/tools`, исполнение на нодах)

---

## 1. Формулировка задачи

Запускать **Personal Assistant** как **доверенный «мозг»** на хосте Synology (или аналоге) с доступом к LLM, памятью и агентским циклом, при этом **опасная или эволюционирующая логика тулов** выполняется на **отдельных сетевых нодах** с меньшей зоной поражения. **Создание** тулов должно опираться на **воспроизводимый пайплайн** (включая опциональную дисциплину `ai-sdlc`), а **не** на неограниченный удалённый shell.

---

## 2. Целевой вижен (сводка)

| # | Элемент | Описание |
|---|---------|----------|
| 1 | **Хост PA («мозг»)** | Работает на Synology (или эквиваленте): маршрутизация LLM, память, агентский цикл, секреты, **каталог тулов** (**YAML**, условие **L**) и хранилище артефактов, оркестрация сборок и раската. |
| 2 | **Удалённые ноды** | Доступные по сети машины, которые могут **исполнять** тулы и при необходимости **запускать builder-контейнеры**. Транспорт и политика — **фазированный гибрид** (см. §7.1): сейчас SSH + политика PA; далее при необходимости VPN, затем **EP-005** (`pa-runner` / subsystem). |
| 3 | **Образ билдера** | Содержит **тулчейн Go**, **закреплённые зависимости** (и/или vendored-модули) и **пайплайн `ai-sdlc`** (skills, спецификация, утилиты валидации), чтобы новые тулы могли разрабатываться в том же процессе, что и продукт, где это уместно. Выпуск артефакта тула — **статический бинарник** (**M**). |
| 4 | **Сценарий создания тула** | **Агентский цикл и вызовы LLM — только на PA** (условия A, **J**). PA **оркестрирует ноду по SSH**: pull/run контейнера билдера (**G**), пошаговое исполнение на ноде (в т.ч. `docker exec`, сборка, `ai-sdlc`); на ноду уходят **команды и согласованная полезная нагрузка**, **не** сырой текст ответа модели. Проверки на ноде (**`validate`** — опционально, **C**). Итог: **статический** бинарник тула (**M**, **B**), архив с ноды **на PA** (**I**, привязка **H**), **git** только на PA, затем запись в **каталог** (**L**). |
| 5 | **Раскат** | После **апрува владельца** (**D**) **PA** доставляет **статический** бинарник (**M**) на ноды **по SSH** (**scp** или **rsync** поверх того же доступа, что **E**), **идемпотентно**, с версией на диске и **откатом** через symlink — условие **N**; вызов — **§7.8**. |

## 3. Опорный поток

```mermaid
sequenceDiagram
  participant PA as PA (Synology: агент, LLM, git, реестр)
  participant Node as Удалённая нода
  participant LLM as LLM API
  participant Git as Git repo

  PA->>Node: SSH: pull / run образа билдера (условие G)
  loop Создание тула (агентский цикл на PA; условие J)
    PA->>LLM: Вызов модели (ключи только на PA)
    LLM-->>PA: Ответ (текст модели остаётся на PA)
    PA->>Node: SSH: шаги на ноде / в контейнере (команды, не prose модели)
    Node-->>PA: stdout/stderr, код выхода
  end
  Note over PA,Node: Архив на PA: по умолчанию scp/sftp pull с PA на ноду (I, тот же SSH что E)
  PA->>Git: commit / push ветки задачи (учётные данные git только на PA)
  Note over PA: Апрув владельца (условие D)
  PA->>Node: Раскат: scp/rsync статического бинарника по SSH (N, после D)
```

## 4. Принципы проектирования (явные)

- **Секреты и основной контур доверия** остаются на **PA**; ноды — **менее доверенные** зоны исполнения. **Ключи LLM только на PA** (условие A); **агентский цикл на PA**; нода **не** инициирует вызовы к LLM (**условие J**). **Учётные данные git** — **только на PA** (условие I); **git push с ноды** не используется.
- **Оркестрация ноды — SSH от PA** (условие J): на ноду передаются **команды и политика** (allowlist, будущий EP-005), **не** универсальный shell и **не** сырой вывод модели как единственный драйвер действий. **Раскат** бинарника на ноды — тот же класс доступа (**E**), направление **PA → нода**, условие **N**.
- **Зависимости** сборки **закреплены** или **заранее вшиты** в образ билдера; ad-hoc `go get` только через **явный allowlist** и ревью.
- **Выпуск в прод** требует **апрува владельца** (условие D) и **метаданных целостности** (checksums / подпись — уточняются).
- **Интеграция `ai-sdlc`** **опциональна по профилю**: полный пайплайн эпика для высокорисковых тулов; облегчённый профиль для мелких утилит (см. `ai-sdlc/specification/pipeline.spec.md`).
- **Валидация на нодах** (`validate`, расширенные проверки) — **опциональна** и зависит от **тяжести тула** (условие C); на PA при необходимости остаётся обязательный контур для эпиков с AC.

## 6. Минусы и риски

| Минус / риск | Примечания |
|--------------|------------|
| **Новая поверхность атаки** | Канал **PA→нода по SSH** и приём **артефактов на PA** (условие I) нужно **спроектировать** (authn/z, replay, лимиты); обратные вызовы контейнера→PA **пока вне модели** (**J**). |
| **PA как ценная цель** | Если PA хранит ключи ко всем нодам, **компрометация PA** масштабируется горизонтально; нужны **scoped**-учётные данные, ротация, минимальная зона поражения на ноду. |
| **Сложность** | Два жизненных цикла: **образ билдера** и **образ рантайма / бинарник** на тул; без multi-platform поверхность проще (условие B). |
| **Тяжесть ai-sdlc** | Полный 9-этапный пайплайн на каждый мелкий тул может быть **избыточен**; нужны **tiered**-профили, чтобы избежать бюрократии. |
| **Размещение LLM** | **Снято:** ключи и агентский цикл только на PA (**A**, **J**); контейнер **не** вызывает LLM напрямую и **на данном этапе** **не** делает обратных вызовов к PA за LLM. |
| **Ограничения Synology** | Docker, права и особенности DSM могут отличаться от «обычного» Linux на нодах. |

## 7. Открытые вопросы

### 7.1 Канал и политика (PA ↔ ноды) - CLOSED

**Текущее состояние продукта (факт):** исполнение на нодах идёт через **SSH** с клиентом PA (`internal/ssh`), удалённая команда — **exec-сессия** (`session.Run`), политика на стороне PA — **allowlist** и каталог тулов. Отдельного бинарника **`pa-runner`** и SSH subsystem (**[EP-005](../../epics/EP-005/ep-scope.md)**) в коде **пока нет**. Скрипт `scripts/deploy-pa-runner.sh` ориентирован на **будущую** поставку бинаря (`cmd/pa-runner` при появлении) и **не** подменяет собой реализацию клиента/сервера в PA.

**Рекомендуемая раскладка — гибрид по ролям и фазам:**

| Фаза | Смысл |
|------|--------|
| **1 — сейчас** | Один транспорт исполнения: **SSH + политика PA** (allowlist и т.д.). При необходимости **VPN** (например Tailscale) только для **достижимости** и стабильных адресов в приватной сети, **без** замены идентичности: ключи и узкий контур остаются на SSH. Разделять «админку» и «рантайм» **разными протоколами** на этой фазе **не требуется** — оба сценария используют тот же путь. |
| **2 — после EP-005** | На ноде — **`pa-runner` + SSH subsystem** (например `pa-exec`); на PA — клиент subsystem; семантика — структурированный запрос без shell в цепочке парсинга полезной нагрузки. **Тот же** сетевой слой (VPN при необходимости) сохраняется. |
| **3 — по необходимости** | Отдельный канал (**mTLS**, **агент с обратным туннелем**) только если после фазы 2 останутся **неудовлетворённые** требования (latency, политика egress, масштаб, NAT без VPN); **не** как обход отсутствия `pa-runner`. |

### 7.2 Модель задачи билдера

- **Pull образа билдера** — зафиксировано как **условие G** (см. §8): оркестрация **с PA удалённо**; отдельный локальный демон как обязательная модель **не** предполагается.
- **Привязка задачи и передача артефактов на PA** — **условие H** (см. §8): **job ID + секрет** или **JWT от PA**; в целевой модели с **J** основной фокус — **передача архива на PA** (I), а не прокси LLM из контейнера.
- Куда попадают **`ai-sdlc-artefacts`** — зафиксировано как **условие I** (см. §8): эфемерная рабочая копия на ноде → **передача на PA** (по умолчанию **scp/sftp pull** с машины PA) → **git commit/push только на PA** (без push с ноды).

### 7.3 Использование LLM и граница данных (агент на PA, оркестрация по SSH)

- **Зафиксировано (A):** ключи и **вызовы LLM** — **только на PA**.
- **Зафиксировано (J):** **агентский цикл** ведётся **на PA**; шаги на ноде **инициирует PA по SSH**; **сырой текст ответа модели на ноду не** передаётся как норма — только **команды и согласованные данные** для исполнения (аргументы, stdin, файлы по политике). **Обратные вызовы** контейнера или ноды к PA за доступом к LLM **на данном этапе не** входят в целевую модель; вариант с прокси из контейнера — **к отдельному обсуждению** позже.
- **Зафиксировано (H, I):** передача итогового **архива** на PA привязана к **job**; **git** только на PA.

**Остаётся открытым** (эпик задачи билдера / SSH-оркестрации):

| Тема | Вопросы |
|------|---------|
| **SSH: форма шагов** | **Рекомендация зафиксирована:** **§7.3.2**. Передача файлов, `scp`, соответствие allowlist и **EP-005**. **Числовые лимиты** — **§7.3.1** (**K**). |
| **Объём данных по SSH** | **Зафиксировано численно:** **§7.3.1**. Принцип: большие патчи и скрипты — **файлом на ноде**, не в argv; полный контекст диалога с моделью на ноду **не** тащить. |
| **Финальная передача архива на PA (I, H)** | **Зафиксировано в I:** по умолчанию **scp/sftp pull** с PA. **Лимиты размера архива** — **§7.3.1**. **Остаётся в эпике:** путь к файлу на ноде, целостность (хеш), **redaction** до git; при превышении лимитов или обрывах — **альтернативы** (rsync по SSH, POST на PA с **H**, object storage). |

**Смысл:** **A** и **J** убирают необходимость протокола «PA↔контейнер для LLM» **сейчас**; открытые вопросы смещаются к **безопасной оркестрации по SSH** и к **приёму артефактов** на PA.

### 7.3.1 Рекомендуемые лимиты размеров (эпик; условие K)

Стартовые значения для реализации и конфигурации PA; **не** жёсткие константы ОС. После метрик (p95 размер лога шага, p95 размер архива) допускается корректировка в эпике.

| Объект | Лимит | Обоснование |
|--------|-------|-------------|
| **Строка одной удалённой команды** (после подстановок, allowlist) | **32 KiB**; жёсткий потолок **128 KiB** | Ниже типичного системного `ARG_MAX`, но длинная строка — сигнал вынести данные **в файл на ноде** отдельным шагом. 32 KiB достаточно для путей и коротких аргументов. |
| **Stdin одного вызова** (`session.Run` и аналог) | **1 MiB** | Хватает для небольшого JSON/diff; **больше** — писать во временный файл на ноде и передавать **путь**, чтобы не раздувать память PA/`sshd`. |
| **Stdout и stderr одного шага** (хранение на PA для лога/агента) | **256 KiB** на поток с усечением и пометкой; опционально **2 MiB** на поток для профиля «тяжёлый тул» | Компромисс для хоста в духе Synology: много шагов подряд не должны съедать RAM; усечение снижает риск DoS логами. |
| **Суммарный лог одной job** (все шаги) | **50 MiB**; жёсткий потолок **200 MiB** | Достаточно для длинной сборки; сверх — ротация (старые шаги в файл на диск / только хвост полностью). |
| **Финальный архив** (scp/sftp pull по **I**) | **512 MiB** по умолчанию; до **2 GiB** с явным профилем «крупный артефакт» | Типичный бинарник + исходники + `ai-sdlc-artefacts` для одного тула; разумное время копирования по LAN. Выше — object storage или rsync/докачка (**эпик**). |

**Связь с условиями:** **I** (архив), **J** (шаги по SSH), **E** (тот же SSH-клиент); при **POST** или object storage лимиты задаются отдельно в эпике, но **принципы** (потолок размера, усечение логов) те же.

### 7.3.2 Форма SSH-шагов (рекомендация для эпика)

Цель — **не** универсальный shell и **не** подстановка произвольной строки от модели в `sh -c`; только **шаблоны** с параметрами из **белого списка** (образ, контейнер, `job_id`, пути workspace — **J**, **K**).

**Не обязательно** выбирать крайность «очень много мелких строк в allowlist». Рациональный **микс:** несколько **именованных шаблонов** на PA (семейства команд с ограниченными подстановками) **плюс** при желании **одна обёртка** на ноде.

| Вариант | Порядок числа шагов / записей | Примечание |
|---------|-------------------------------|------------|
| **Много явных docker-шагов** (без обёртки) | **10–20** уникальных шаблонов на полный цикл (pull, run/exec, сборка, `ai-sdlc`, архив, …) | Каждый смысл отдельно в allowlist. Профили **C** могут добавить **2–5** вариантов (например отдельный шаг под `validate`). |
| **Обёртка на ноде** (`pa-builder-step.sh` или аналог с подкомандами) | **3–7** высокоуровневых вызовов со стороны PA | Внутри скрипта — обычный `docker`, но **не** из произвольного текста LLM; скрипт версионируется и деплоится на ноду. |
| **После [EP-005](../../epics/EP-005/ep-scope.md)** (subsystem) | Меньше **строк** shell allowlist; **логически** те же **~5–10 типов** операций | Полезная нагрузка — структурированный `argv[]`, не разбор shell. |

**Стартовая рекомендация для прототипа:** **одна обёртка на ноде + 5–8 явных шаблонов** `docker …` на PA (pull, run, ключевые `exec`, упаковка архива под **I**), затем по мере усложнения — **дробить** шаблоны или переходить к **EP-005**, не раздувая allowlist без нужды.

**Оценка для планирования эпика:** заложить **~15 ± 5** **именованных** типов шагов в дизайне; точное число вывести из **одного** сквозного сценария «создать тул от старта job до архива на PA».

### 7.4 Артефакты и реестр

- **Семантика registry / каталога** — зафиксировано как **условие L** (см. §8): **каталог для агента — YAML**; **БД опционально**; **версия по дате/времени**; **digest** обязателен для целостности бинарника; **подпись** (cosign и т.п.) — опционально в эпике.
- ~~**Мультиплатформа**~~ — **вне объёма** (условие B): один бинарник под согласованную платформу.
- **Линковка выпускаемого тула** — зафиксировано как **условие M** (см. §8): **статический Go-бинарник** (`CGO_ENABLED=0` по умолчанию), без зависимости от **glibc/musl** на нодах при согласованном **GOOS/GOARCH** (**B**).

### 7.5 Гейты качества — частично закрыто условием C

- Точный гейт: эквивалент **`make check`** в **минимальной раскладке модуля** для сгенерированных тулов?
- **`./bin/validate EP-XXX`** на **ноде**: **опционален**, зависит от **тяжести тула**; для эпиков с AC в `ai-sdlc-artefacts` полный **`validate` на PA** (или в CI до передачи артефакта) может оставаться обязательным **независимо** от ноды — уточнить в эпике.

### 7.6 Апрув — закрыто условием D

- **Зафиксировано:** апрувит **владелец**.
- **Остаётся открытым:** **что** входит в пакет на ревью (diff, `go.sum`, SBOM, чеклист угроз) — рекомендуемый состав, не альтернатива апруву владельца.

### 7.7 Раскат на ноды — зафиксировано как условие **N** (см. §8)

**Целевой механизм (MVP вижена):** после **апрува владельца** (**D**) **PA** инициирует доставку **статического** бинарника тула (**M**) на выбранные ноды **по SSH** (**E**): **`scp`** или **`rsync`** в направлении **PA → нода** (обратно потоку архива **I**). Команды и пути — **отдельные шаблоны allowlist** (или subsystem **EP-005**), согласованные с **§7.3.2**, не смешивать произвольно с шагами билдера (**J**).

**Идемпотентность:** повторный раскат той же версии **перезаписывает** согласованный путь (или no-op, если digest совпадает — **эпик**).

**Версии на диске ноды:** бинарник в каталоге с **именем, включающим версию** (дата/время по **L** или короткий **digest**) **и/или** symlink **`current` →** конкретный файл; точная схема — **эпик**, принцип — несколько файлов на диске, переключаемый **`current`**.

**Откат:** переключение **`current`** (или эквивалента) на **предыдущую** сохранённую на ноде версию **или** повторная выкладка предыдущего артефакта с PA по записям **L**/хранилища (**эпик**).

**Здоровье после раската:** минимум — файл на месте, права исполнения; опционально сверка **digest** с каталогом (**L**); опционально **безопасный** тестовый вызов (в allowlist) — **эпик**.

**Вне целевой модели по умолчанию** (только при отдельном решении в эпике): **OCI-образ на каждый тул**, **системные пакеты** (`.deb`/rpm), **configuration management** для малого числа нод.

### 7.8 Вызов в рантайме

- На **фазах 1–2** (см. §7.1) целесообразен **тот же канал**, что и для прочего доступа PA к ноде (SSH; после EP-005 — тот же SSH с режимом subsystem для исполнения). Отдельный канал «только для исполнения» — предмет **фазы 3**, если появятся отдельные требования.
- Путь к исполняемому файлу на ноде согласуется с **раскатом** (**N**) и записью **YAML-каталога** (**L**) — **эпик**.

## 8. Принятые условия (зафиксировано для этого вижена)

| # | Условие | Смысл |
|---|---------|--------|
| A | **Ключи LLM только на PA** | Вызовы LLM и хранение API-ключей — **только** на PA. **Агентский цикл** ведётся **на PA** (**J**); нода и контейнер билдера **не** инициируют вызовы к провайдеру LLM. |
| B | **Мультиплатформенная сборка не требуется** | Достаточно **одной целевой платформы** (один `GOOS`/`GOARCH` или фиксированный набор нод одного типа). Кросс-компиляция и матрица артефактов **вне объёма** этого вижена. Выпускаемый бинарник тула — **статический** (**M**). |
| C | **Валидатор (`validate` и аналоги) на нодах опционален** | Запуск **`./bin/validate`** (или эквивалента) на ноде **не** обязателен по умолчанию; решение зависит от **тяжести/риска тула** (лёгкая утилита vs эпик с AC в `ai-sdlc-artefacts`). Тяжёлые тулы могут требовать полного контура проверок; простые — обходятся гейтами только на PA или минимальной проверкой в билдере. |
| D | **Апрувит владелец** | Решение о **включении тула в прод** и **раскате на ноды** принимает **владелец** системы (однозначно, без обязательного второго лица или отдельного CI-гейта как замены человеку, если иное не введут позже). Раскат выполняется **только после** этого решения (**N**). |
| E | **Идентичность PA↔ноды** | **SSH-ключи** — **основа**: долгоживущая аутентификация и привязка к ноде (выделенный пользователь на ноду, проверка host key). **Короткоживущие токены / API к PA** — **опционально** для вспомогательных контуров (например приём артефактов — **H**, **I**); **обратные вызовы за LLM** с ноды **пока вне модели** (**J**). **SPIFFE** — **избыточны** и **вне объёма**. |
| F | **Связность при NAT / без входящего SSH** | Если нода **не** доступна для **прямого** TCP от PA (CGNAT, firewall, политика «только исходящие»), **целевой** способ — **VPN / mesh с исходящей регистрацией ноды** (например Tailscale), после чего PA подключается по SSH к **стабильному адресу в приватной сети** (условие E не меняется). **Фаза 3** (агент с **обратным** туннелем или отдельный канал) — **если VPN недоступен или неприемлем** по политике. Сценарий «PA обязан сам пробить NAT к ноде без VPN и без reverse» **не** считается целевым для этого вижена. Конкретный продукт VPN и ACL — по среде развёртывания. |
| G | **Pull образа билдера на ноду** | **PA** инициирует и оркестрирует pull **удалённо** по тому же каналу PA→нода, что и для прочего доступа к ноде (например SSH: на ноде выполняется команда `docker pull` / эквивалент под политикой). Обязательный **локальный демон** на ноде только для pull **не** входит в целевую модель этого вижена; при необходимости фоновые ретраи или предзагрузка образов — **опциональное** улучшение среды, **без** замены оркестрации с PA. |
| H | **Привязка задачи (job)** | **Job ID** + **секрет** или **подписанный JWT от PA** (короткий срок) связывают задачу с **доставкой артефактов на PA** (**I**) и записями на PA. В модели **J** это **не** про прокси LLM из контейнера **на данном этапе**; обратные вызовы за LLM, если появятся позже, используют **тот же** принцип привязки job. **OAuth** (device flow) и обязательный **mTLS** для этого вижена **не** целевые. Детали — в эпике. |
| I | **Публикация `ai-sdlc-artefacts` и исходников** | Рабочая копия при генерации — на **эфемерном томе** (контейнер/нода). **Публикация в git** — **только на PA**: на ноде **нет** учётных данных git и **нет** `git push`. **Доставка архива на PA** (исходники, `ai-sdlc-artefacts`, бинарник **B** + **M**): по умолчанию **scp** или **sftp** в режиме **pull с хоста PA** — команда на **PA** копирует файл **с ноды** в локальную ФС PA (тот же **SSH** к ноде, что **E**; отдельный входящий SSH **на** PA от ноды **не** требуется). Привязка к **job** — в логике PA (**H**). **Числовые лимиты размера архива** — **§7.3.1** (**K**). **Альтернативы** (POST на PA с JWT, **rsync** по SSH, object storage) — при превышении лимитов **K**, нестабильной сети или политике, где подсистема `scp`/`sftp` ограничена — **эпик**. **Учётные данные git** — **только на PA** (отдельно от ключей LLM, **A**). **PA** выполняет **commit** / **push**, **ветка на задачу** (например `job/<job-id>`), затем проверки и апрув (**D**). Крупные бинарники при необходимости — вне git. Детали путей, `.gitignore`, merge — в эпике. |
| J | **Оркестрация сборки на ноде** | **Агентский цикл** и **вызовы LLM** — **только на PA** (**A**). Шаги на ноде (в т.ч. `docker pull` / `run` / `exec`, сборка, `ai-sdlc`, `make check`) **инициирует PA удалённо по SSH** (**E**, allowlist; далее **EP-005**). На ноду уходят **команды и согласованная полезная нагрузка**, **не** сырой текст ответа модели как основной способ управления. **Рекомендуемая форма шагов** (обёртка vs шаблоны, оценка числа) — **§7.3.2**. **Обратные вызовы** контейнера или ноды к PA **для доступа к LLM** **на данном этапе не** входят в целевую модель; вариант с таким прокси — **к отдельному обсуждению** позже. |
| K | **Лимиты размеров (SSH и артефакты)** | Стартовые **числовые** ограничения на длину команды, stdin, stdout/stderr и лог job, размер финального архива (**I**) — **§7.3.1**. Задают защиту от чрезмерного потребления памяти/диска на PA, от раздувания argv и от долгих нестабильных передач; **не** заменяют настройку `sshd`/ОС. Корректируются по метрикам после реальных прогонов. |
| L | **Каталог тулов и артефакты на PA** | **Каталог** (источник правды для агента по выбору тула, политике и версии) хранится в **YAML** (один файл или дерево файлов — **эпик**). **БД** (например SQLite/PostgreSQL) — **опционально** как индекс/кэш или для UI, но **семантика** записей должна соответствовать YAML-каталогу (или быть его проекцией). **Бинарники** — в отдельном **хранилище** (файловая система или объектное); в каталоге — **путь или ключ**, **digest** (например SHA-256) и метаданные. **Версионирование записи** — по **дате и времени** выпуска/публикации на PA (рекомендуется **UTC**, формат в духе ISO 8601; точность до секунды — **эпик**). **Подпись** артефакта (Sigstore/cosign и т.д.) — **опционально**, не требование этого вижена. Связь с апрувом владельца (**D**) и git артефактов (**I**) — в эпике. |
| M | **Статический бинарник тула (Go)** | Выпускаемый **исполняемый файл тула** собирается как **полностью статический** бинарник Go: по умолчанию **`CGO_ENABLED=0`** для **релизной** сборки артефакта, чтобы на целевых нодах **не** зависеть от версии **glibc** или **musl** при согласованном **GOOS/GOARCH** (**B**). Сборка в **образе билдера** (§2) должна **по умолчанию** применять эту политику к генерируемым тулам. **Исключения** (необходимый **cgo**, внешние `.so`) — **только** с **явным апрувом владельца** (**D**) и с отдельной фиксацией в **эпике** минимального ABI, базового образа или политики нод. Внутренние бинарники самого PA **вне объёма** этого условия, если иное не согласуют отдельно. |
| N | **Раскат на ноды** | **Только после апрува владельца** (**D**). **PA** доставляет бинарник тула (**M**) на ноды **по SSH** (**E**): **`scp`** или **`rsync`** **PA → нода** (противоположно **pull** архива **I**). **Идемпотентность** — перезапись согласованных путей (или эквивалент в **эпике**). **Несколько версий** на диске ноды — имя с версией (**L**) и/или **digest**; переключение через symlink **`current`** (или эквивалент) — **эпик**. **Откат** — переключение на предыдущую версию или повторная выкладка с PA. **Проверки после раската** — файл, права, опционально **digest** и безопасный тестовый вызов — **эпик**. Шаблоны allowlist для раската — **отдельно** от шаблонов билдера (**J**), см. **§7.3.2**. **OCI на тул**, **пакеты ОС**, **Ansible** и т.п. — **вне** целевой модели по умолчанию, только по отдельному решению в **эпике**. |

Эти условия сокращают перечень открытых вопросов в **разделе 7**; соответствующие подпункты там помечены или сокращены.

## 9. Аналоги (справочно)

Паттерны похожи на **self-hosted CI runners** (GitLab Runner, GitHub Actions runner), **удалённые Docker/BuildKit builders**, **продвижение подписанных артефактов** (Sigstore/cosign, GoReleaser) и **деплой с политикой** — не одна готовая продуктовая линка, закрывающая этот вижен целиком.

Для контраста см. также: `analytics/goclaw/goclaw-analysis.md` (политика тулов вокруг gateway и песочница).

## 10. Следующие шаги (предложение)

1. Закрепить **фазу 1**: при необходимости **VPN** (**F**) + **SSH + политика PA**; оркестрация сборки тула с **агентом на PA** (**A**, **J**). **Не** планировать второй транспорт исполнения до **EP-005** (`pa-runner` / subsystem). Скрипт `deploy-pa-runner.sh` — **после** появления бинаря и клиента subsystem.  
2. Зафиксировать **модель данных каталога тулов** на PA (**L**): YAML, версия по дате/времени, digest; опционально БД и подпись — по эпику (**B** — одна платформа, **M** — статическая сборка тула).  
3. Определить **два профиля ai-sdlc** (полный эпик против облегчённый) и правила, когда **`validate` на ноде** обязателен vs опционален (условие C).  
4. Описать **чеклист апрува владельца** (условие D): минимальный набор артефактов для решения о раскате.  
5. Сделать **один** сквозной прототип: **агент на PA** + **SSH-оркестрация** ноды (**J**) → передача архива на PA (**I**, **H**) → **git push с PA** → **апрув владельца** (**D**) → **раскат** бинарника на вторую ноду (**N**) → вызов из PA (**§7.8**).
