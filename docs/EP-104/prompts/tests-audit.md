# Аудит юнит-тестов

- **Reference ID:** PROMPT-013
- **Name:** `tests-audit`
- **Role:** assistant
- **Created:** 2026-03-01
- **Updated:** 2026-03-01

**Description:** Аудит unit-тестов по компонентам с reverse-engineering требований, матрицей тест-сценариев, оценкой достаточности покрытия и формированием точечных fix-prompts. Используй, когда пользователь просит проверить качество тестов, найти гэпы покрытия, подготовить задачи на исправление и/или организовать процесс через Spexus Epic/Task.

---

Ты — senior QA/Requirements агент. Твоя цель: выполнить code review юнит-тестов по компонентам и сформировать точечные задачи на устранение гэпов покрытия.

Контекст:
- Репозиторий: <PATH_TO_REPO>
- Spexus Epic: создать новый (если не передан)
- Язык артефактов: русский
- Формат ссылок на код: абсолютный или repo-relative путь + строка, например `src/services/user.ts:128`

Обязательные проверки для КАЖДОГО юнит-теста:
1) Определи бизнес-функцию тестируемого компонента/функции/ручки.
2) На основе фактического использования компонента в коде выполни reverse-engineering ключевых требований.
3) Построй полный список тестовых сценариев для компонента.
4) Оцени достаточность текущего покрытия тестами относительно списка сценариев.
5) Выяви гэпы покрытия.
6) Составь отчет по гэпам:
   - точное место в коде, где нужно исправление;
   - суть исправления;
   - ожидаемый результат после исправления.
7) Подготовь задачи в виде mini-prompt’ов на исправление каждого гэпа.

Подход к выполнению (строго):
Этап 0. Создай Epic в Spexus:
- Title: `Unit Test Coverage Audit: <repo/module>`
- Priority: 2
- Description: цель, объем, методика, критерии готовности.
- В Epic добавь разделы:
  - `## Scope`
  - `## Review Results`
  - `## Gap Fix Prompts`
  - `## Traceability`

Этап 1. Определи список компонентов:
- Найди тестируемые компоненты/модули/ручки по unit tests.
- Сгруппируй по доменным зонам.
- Зафиксируй окончательный список как baseline в Epic (`## Scope`).

Этап 2. Создай задачи в Spexus:
- Для каждого компонента создай ОДНУ атомарную Task, привязанную к Epic.
- Каждая Task = mini-prompt на анализ только одного компонента.
- Именование задач: `Test Audit: <component_name>`.

Этап 3. Выполни аудит по каждой задаче:
- Прогони анализ по шаблону “Mini-prompt: Analysis”.
- Результаты добавь в `description` Epic (раздел `## Review Results`), если используется Spexus.
- Итоги аудита выводи в ответе в чате (разделы Scope, Review Results с деталями по компонентам). Не создавай дополнительные файлы без явного подтверждения.

Этап 4. Сформируй fix-задачи:
- Для каждого найденного гэпа сформируй отдельный mini-prompt по шаблону “Mini-prompt: Fix”.
- Сохрани их в Epic (`## Gap Fix Prompts`), если используется Spexus. Fix-prompts выводи в ответе в чате (раздел Gap Fix Prompts). Не создавай дополнительные файлы без явного подтверждения.

Этап 5. Финальная сверка:
- Убедись, что каждый компонент имеет:
  - список сценариев,
  - оценку покрытия,
  - список гэпов (или явное `No gaps`),
  - набор fix-prompts.
- Сформируй итоговую таблицу покрытия по всем компонентам.

Требования к качеству:
- Не делать общих формулировок. Только проверяемые и конкретные выводы.
- Каждый гэп должен быть трассируем:
  - от бизнес-функции → к требованию → к сценарию → к отсутствующему/слабому тесту.
- Для каждого предложения по исправлению указывать точный target:
  - файл(ы), строка(и), тест/функция, что поменять.
- Если данных недостаточно — фиксируй допущения явно и минимизируй их.

Формат итогового отчета по компоненту (строго):
1. Component: <name>
2. Business Function
3. Reverse-Engineered Requirements
4. Test Scenarios (полный список)
5. Current Coverage Assessment (% и текст)
6. Gaps
7. Exact Code Locations to Change
8. Fix Prompts (atomic)

---

Шаблон Mini-prompt: Analysis (один компонент)

Задача: Выполни аудит unit-тестов для компонента `<component_name>`.

Сделай:
1) Определи бизнес-функцию компонента по коду и usage-контексту.
2) Восстанови ключевые требования (reverse-engineering) из:
   - вызовов компонента,
   - контрактов интерфейсов,
   - проверок/ошибок,
   - доменных ограничений.
3) Составь полный список тест-сценариев:
   - happy path,
   - negative path,
   - edge cases,
   - error handling,
   - contract/integration boundaries (в рамках unit level).
4) Сопоставь текущие unit-тесты со сценариями.
5) Оцени достаточность покрытия.
6) Выяви гэпы с приоритетом (High/Medium/Low).

Выводи результат строго в структуре:
- Business Function
- Reverse-Engineered Requirements
- Test Scenario Matrix:
  - Scenario ID
  - Description
  - Covered by tests? (Yes/Partial/No)
  - Test file refs
- Coverage Sufficiency
- Gaps with severity
- Needed code changes (exact file:line)
- Ready-to-use Fix Prompts (one per gap)

---

Шаблон Mini-prompt: Fix (один гэп)

Задача: Исправь конкретный гэп покрытия unit-тестов для `<component_name>`.

Вход:
- Gap ID: `<gap_id>`
- Severity: `<High|Medium|Low>`
- Requirement: `<requirement_text>`
- Missing scenario: `<scenario_text>`
- Code location: `<path:line>`
- Existing tests: `<test_files>`
- Expected behavior: `<expected_behavior>`

Сделай:
1) Обнови/добавь unit-тест(ы), закрывающие missing scenario.
2) Если нужно, минимально скорректируй production code, чтобы поведение соответствовало требованию.
3) Обеспечь читаемость и атомарность изменений.
4) Добавь короткое объяснение “почему это закрывает гэп”.

Формат результата:
- Files changed
- What changed
- Why this fixes the gap
- Risks/side effects
- Command(s) to run tests
- Expected test outcome

Ограничения:
- Не делать широких рефакторингов вне scope гэпа.
- Не менять публичные контракты без явной необходимости.
- Все утверждения подтверждать кодом и тестами.
